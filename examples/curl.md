## Notes

* `curl` treats command-line arguments that are not options or option values as URLs.
* A single invocation can transfer multiple URLs and may reuse existing connections between requests.
* A plain `curl URL` performs a GET request by default.
* `-d`, `--data`, and related options imply POST unless another HTTP method is explicitly specified.
* `--json` is convenient for JSON APIs because it sends the body as JSON and configures the relevant JSON headers automatically.
* `-I` performs a HEAD request and retrieves response headers without downloading the response body.
* `-i` differs from `-I`: it includes the response headers together with the normal response body.
* `-L` should be used when the endpoint may return HTTP redirects.
* `-o` specifies a local filename, while `-O` uses the filename from the remote URL.
* `-sS` is preferable to `-s` in many scripts because errors remain visible.
* `-fsS` is a practical default for shell scripts when the response body is only relevant on success.
* `--fail-with-body` is useful when debugging APIs because it returns a failing exit status while still preserving the error response body.
* Avoid unnecessarily using `-X POST` when using `-d` or `--json`; those options already make curl use POST.
* `-k` / `--insecure` disables TLS certificate verification and should not be used as a routine workaround in production.
* Avoid putting passwords, API keys, or long-lived tokens directly in shell commands when possible because they may be exposed through shell history, process inspection, or logs.
* For JSON APIs, `curl` and `jq` are especially useful together:

```bash
curl -fsS https://api.example.com/users | jq '.'
```

* For automated health checks, this pattern is usually preferable to plain `curl`:

```bash
curl -fsS https://api.example.com/health
```

* When you need the server's error body as well:

```bash
curl -sS --fail-with-body https://api.example.com/health
```
